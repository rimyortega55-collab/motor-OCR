Contrato de API para el frontend

Lo que el SPA de React necesita del FastAPI. Los pasos 1, 2 y 3 — sesión, API keys, listado, procesamiento asíncrono y los bloques que hacen posible el visor de revisión — ya están implementados y con pruebas. Falta el paso 4 (umbrales por usuario) y el 5 (consumo y exportación).

01

Tres prerrequisitos de almacenamiento

resueltos

No son endpoints, pero sin ellos la mitad del contrato no se puede implementar. Los tres salieron de leer el pipeline, no de suponer.

1.1  Los bloques no se persisten

POST /procesar calcula miles de Bloque y los tira. _resumir_documento guarda en documentos.resultado sólo conteos por tipo, confianza media y la lista de inconsistencias. El visor de revisión necesita los bloques uno por uno, así que hace falta una tabla bloques:

columnatiponota
idString(36) PKel Bloque.id
documento_idFK CASCADEindexado
paginaInteger0-based, como en el pipeline
orden_lecturaIntegerde Layout.orden_lectura
tipoString(30)valor de TipoBloque
origen_contenidoString(20)texto_nativo / requiere_ocr
bboxJSONnormalizado, ver 1.3
confianza_layoutFloat
confianza_globalFloat?Ocr.confianza_global
texto_plano · latexText?
contenido_finalText?lo que dejó la revisión humana
micro_segmentosJSONlista de MicroSegmento
escalacionJSON?el Escalacion del bloque
estado_revisionString(20)pendiente / resuelto / no_requiere

Índices: (documento_id, pagina, orden_lectura) para el visor y (documento_id, estado_revision, confianza_global) para armar la cola. Una fila por bloque en vez de un JSON gigante en documentos.resultado, porque la cola filtra y pagina sobre 31 000 bloques: deserializar el documento entero en cada request no escala.

1.2  El PDF original se borra

api.py hace ruta_temporal.unlink(missing_ok=True) en el finally. Para servir la imagen de una página hay dos caminos: guardar el PDF y renderizar a demanda con caché, o guardar los PNG ya renderizados de las páginas con bloques en la cola.

Recomendación: guardar el PDF y renderizar a demanda. El visor sólo pide las páginas que el revisor abre, que son pocas. Esto obliga a una política de retención explícita: hay que decir por cuánto tiempo queda el PDF y borrarlo al borrar la cuenta.

1.3  El bbox no tiene un espacio de coordenadas único

Bug latente

segmentation/nativo_digital.py toma el bbox de PyMuPDF, en puntos PDF a 72 dpi. segmentation/escaneado.py lo toma de docTR, en píxeles al DPI de render. escalation/_recortar_bloque indexa la imagen renderizada con el bbox crudo, lo cual sólo es correcto para el segundo caso.

Hoy no falla porque los bloques nativos son TEXTO_NATIVO, la Capa 3 los saltea y nunca tienen micro-segmentos que escalar. El overlay del visor sí los dibuja a todos: un bloque nativo se dibujaría a ~36 % de su tamaño real sobre una página a 200 dpi.

Decisión del contrato: la API devuelve bbox siempre normalizado a la caja de la página, cuatro flotantes en [0, 1].

"bbox": { "x0": 0.128, "y0": 0.442, "x1": 0.871, "y1": 0.509 }

El frontend multiplica por el tamaño en píxeles de la imagen que recibió y no necesita saber el DPI ni qué camino de segmentación produjo el bloque. La conversión se hace una vez al persistir: dividir por page.rect en el camino nativo y por (ancho_px, alto_px) en el escaneado. Conviene arreglar _recortar_bloque en la misma pasada.

02

Convenciones

Autenticación

Dos credenciales que resuelven al mismo Usuario:

  • Navegador: cookie motor_ocr_sesion, HttpOnly, Secure, SameSite=Lax. No se guarda la API key en localStorage: es un secreto de larga vida y cualquier XSS se la lleva.
  • Máquinas: cabecera X-API-Key, como hoy.

La dependencia usuario_actual pasa a aceptar cualquiera de las dos. Los endpoints de sesión sólo aceptan cookie; los de datos aceptan ambas.

Errores

Cuerpo uniforme, para ramificar sin parsear texto. 404 y no 403 para recursos de otro usuario, como ya hace _documento_del_usuario.

{ "codigo": "limite_plan_superado", "detail": "El plan libre permite 200 páginas por mes" }

Prefijo

Toda la API cuelga de /api. Las rutas de esta página se escriben sin él por brevedad: GET /documentos es GET /api/documentos.

Por qué

Sin el prefijo, /documentos sería a la vez el endpoint de datos y la ruta principal del SPA, y un navegador que entrara ahí recibiría JSON en vez de la aplicación. Todo lo que no empiece con /api lo resuelve el router de React.

Paginación

?limite= y ?cursor=, keyset sobre (pagina, orden_lectura). Con 31 000 bloques por documento, OFFSET profundo obliga a la base a recorrer todo lo salteado.

{ "items": [...], "siguiente_cursor": "14:0042", "total": 4812 }

Fechas en ISO 8601 UTC con Z. Páginas 0-based en toda la API, igual que en el pipeline; la interfaz muestra 1-based y convierte.

Procesamiento asíncrono

implementado
POST/procesarimplementado · sin opciones

Hoy corre el pipeline completo dentro del request y devuelve el resultado. Un PDF de 92 páginas tarda minutos: el navegador corta por timeout mucho antes.

multipart/form-data: file=<pdf>, opciones=<json>
→ 202 { "documento_id": "…", "estado": "en_cola" }

type OpcionesProceso = {
  idioma_original?: string    // "es"
  dpi?: number | "auto"       // "auto" = lo que decida el triage
  escalar_llm?: boolean       // default true
  tope_gasto_usd?: number     // corta la Capa 5, el resto va a revisión humana
}

tope_gasto_usd no existe en el motor: hay que chequearlo en el bucle de escalation.procesar_escalaciones antes de cada llamada y, al alcanzarlo, marcar los bloques restantes como estado_revision="pendiente" en vez de escalarlos.

Dónde corre el pipeline

Para una instancia alcanza BackgroundTasks de FastAPI. Para varias hace falta una cola real — RQ, Celery, arq — porque BackgroundTasks muere con el proceso y el documento queda en procesando para siempre. En los dos casos hace falta un barrido que marque como error lo que lleve demasiado tiempo en ese estado.

  "capas": [
    { "capa": 1, "nombre": "triage",       "estado": "completada",
      "detalle": "92 páginas · nativo digital · 3 zonas de DPI" },
    { "capa": 2, "nombre": "segmentacion", "estado": "completada",
      "detalle": "11940 bloques · 12 tipos" },

      "detalle_engines": { "easyocr": 4210, "pix2tex": 512, "doctr": 170 } },
    { "capa": 4, "nombre": "correccion",   "estado": "pendiente" },
    { "capa": 5, "nombre": "escalacion",   "estado": "pendiente" }
  ],
  "costo_usd_parcial": 0.0,

  "error": null
}

Estado del documento: en_cola · procesando · completado · error. De cada capa: pendiente · en_curso · completada · omitida.

El pipeline hoy no reporta nada mientras corre: hace falta que Pipeline.ejecutar acepte un callback de progreso y que el worker lo vuelque a la fila del documento. Se puede considerar SSE en /documentos/{id}/eventos, pero polling cada 2 s alcanza para empezar y es mucho más simple de operar.

GET/documentosimplementado

Acepta ?estado=, ?buscar= por título (sin distinguir mayúsculas), ?necesita_revision=, ?limite= y ?cursor=. Devuelve {items, siguiente_cursor, total}, un cambio de forma respecto de la lista suelta anterior.

El orden es (creado_en DESC, id DESC). El id desempata a propósito: dos documentos subidos en el mismo instante harían que el cursor saltee o repita filas si el orden no fuera total.

Falta guardar la corrección del modelo

contenido_llm no existe hoy en el modelo Escalacion del motor: EscalationResult trae contenido_final pero se pierde al aplicarse. El panel de revisión compara «motor» contra «corrección del modelo», así que hay que guardar los dos.

La cola de revisión no es un endpoint aparte, es este mismo con ?estado_revision=pendiente&orden=confianza. Uno separado duplicaría los filtros.

GET/documentos/{id}/paginasimplementado
{ "total_paginas": 34,
  "paginas": [ { "pagina": 0, "ancho_px": 1654, "alto_px": 2339,
                 "dpi": 200, "bloques": 141 } ] }

El frontend necesita ancho_px/alto_px para desnormalizar los bbox antes de que cargue la imagen, y así reservar el espacio sin saltos de layout.

GET/documentos/{id}/paginas/{n}implementado
→ 200 image/png
    Cache-Control: private, max-age=86400
    ETag: "<documento_id>:<n>:<dpi>"
→ 404 si la página no existe o el documento no es del usuario

Query opcional ?ancho= para pedir una versión reescalada — el visor a 86 % no necesita 1654 px. Sirve la página completa, no el recorte: el overlay se dibuja encima en el cliente, y así una misma imagen sirve para todos los bloques de la página.

06

Revisión

implementado
POST/revision/{documento_id}/decisionimplementado
El feedback loop está cortado acá

El cuerpo actual no manda tipo_bloque, pagina ni confianza_engine, así que se guardan como "", 0 y 0.0. Y AjustadorUmbrales.calcular_umbrales_optimos agrupa las decisiones por d['tipo_bloque'], que siempre vale "". El auto-ajuste no puede aprender nada.

El servidor los completa desde el bloque, no el cliente:

{ "bloque_id": "…", "decision": "aceptar"|"rechazar"|"editar"|"escalar",
  "contenido_final": "…", "confianza_usuario": 0.9, "comentarios": "" }
→ 200 { "decision_id": 12, "siguiente_bloque_id": "…" | null }
→ 422 codigo=bloque_no_pertenece_al_documento

Además la decisión debe escribirse en el bloque: contenido_final y estado_revision="resuelto". Hoy sólo se registra en decisiones y el bloque queda igual, con lo que la exportación seguiría entregando el texto sin corregir.

siguiente_bloque_id evita un round-trip: el visor avanza sin volver a pedir la cola.

POST/revision/{documento_id}/decisionesnuevo

Lote, mismo cuerpo en una lista. Para «aceptar todo lo que quedó arriba de 0.9».

07

Umbrales

Los umbrales son globales y viven en un archivo

AjustadorUmbrales lee y escribe umbrales_config.json con ruta relativa y sin usuario. Es la misma trampa que ya se corrigió en persistence — el archivo se escribe en el cwd y se pierde en cada despliegue — y además haría que un usuario le cambiara los umbrales a todos los demás. Pasan a una tabla umbrales con usuario_id.

GET/umbralesexiste · por usuario
{ "capa3": { "parrafo": 0.75, "formula_display": 0.70, … },
  "capa4": { "estructura_rota": 0.80, "inconsistencia": 1.00 },
  "globales": { "umbral_confianza_engine": 0.75,
                "umbral_escalacion_micro_segmento": 0.6,
                "umbral_confianza_global_escalacion": 0.70 },
  "actualizado_en": "2026-08-24T18:00:00Z" }
PUT/umbralesnuevo

Los sliders de la pantalla. Acepta un objeto parcial con la misma forma, valida 0 ≤ v ≤ 1 y devuelve el estado completo resultante.

GET/umbrales/recomendacionesnuevo

Los calcula sin aplicarlos. Hoy POST /auto-ajuste calcula y aplica en un solo paso, así que la pantalla no puede mostrar la propuesta antes de decidir.

{ "decisiones_analizadas": 47,
  "recomendaciones": [
    { "ambito": "capa3", "clave": "formula_display",
      "actual": 0.60, "propuesto": 0.68, "confianza": 0.82,
      "razon": "62 % de rechazos sobre lo que el motor daba por bueno",
      "aplicable": true } ] }

aplicable reproduce UmbralOptimo.aplicable(): confianza > 0.7 y cambio > 0.02.

POST/umbrales/aplicarreemplaza /auto-ajuste

Recibe las claves a aplicar (o todas las aplicables), guarda un backup y devuelve el resultado de la validación.

La validación hoy es simulada

AjustadorUmbrales.validar_cambios devuelve valores fijos, con "razon": "Simulado - requiere validación real". La pantalla muestra «revertido automáticamente porque la confianza bajó 4.1 %», que sería inventado. O se implementa la validación contra un lote real, o el endpoint devuelve validacion: null y la interfaz no promete lo que no hace.

Y GestorDecisiones._decisiones_cache es un diccionario de módulo: se vacía en cada reinicio, así que el auto-ajuste sólo ve las decisiones de la sesión actual. Debe leer de la tabla decisiones.

Requiere mover la clave de la fila usuarios a una tabla api_keys con usuario_id, para que un usuario pueda tener varias y revocar una sin perder las demás.

10

Exportación

GET/documentos/{id}/exportnuevo

?formato=graphify|markdown|ipynb. Devuelve el documento con contenido_final aplicado donde la revisión humana lo haya dejado, cayendo a latex o texto_plano cuando no. graphify es el JSON de bloques que consume el indexador; los otros dos son archivos.

Para documentos grandes conviene generarlo como job y devolver 202 con una URL de descarga, en vez de armar 31 000 bloques dentro del request.

El orden importa porque el paso 4 depende del 3, y el 3 es el caro:

  1. Sesión y lista. hecho auth/*, api-keys/* y GET /documentos con filtros y cursor, con pruebas en test_auth_api.py. El SPA ya puede arrancar contra esto.
  2. Jobs. hecho POST /procesar asíncrono y GET /estado, con el callback de progreso en Pipeline. Falta opciones y los límites de plan.
  3. Bloques. hecho Tabla bloques, retención del PDF, bbox normalizado, GET /bloques y /paginas/{n}. El visor de revisión ya funciona.
  4. Umbrales. Falta: umbrales por usuario en la base y GestorDecisiones leyendo de la tabla decisiones en vez de su caché en memoria. La decisión ya escribe el bloque y guarda el tipo, que era lo que tenía cortado el loop.
  5. Consumo y exportación.
